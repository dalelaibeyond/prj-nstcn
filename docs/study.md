# `/goal` 项目复盘与提示词优化

复盘日期：2026-10-04。依据：[会话记录](session-10.03.md)、[交付与验证报告](../goal-run/REVIEW.md)、[运行说明](../goal-run/README.md)及[参考规格](spec.md)。本文回顾网站目标；更早的 `AGENTS.md` 请求因环境中断未完成，不能与网站交付混为一谈。会话记录保存的是 Goal 目标正文，不保证与最初键入的命令逐字一致。

## 1. 结论：让一个 Goal 对应一个可完成的阶段

本次最大的改进点，是从一开始就把“可供审阅的网站”与“可以正式上线的网站”拆开。

原目标同时要求“只能使用占位内容”“占位必须明确标识”与“上线检查中占位零命中”。这些条件无法同时满足。`/goal` 能持续推动工作，却不能消除验收条件之间的矛盾。目标越持久，错误的完成条件越容易导致重复检查与阻塞报告。

你后来明确要求先完成审阅版，并将 `spec.md` 改为参考。我完成了这一阶段，但后续自动核查仍沿用原来的上线目标。这说明实现范围已经调整，持久目标的完成条件却没有同步对齐。

更好的安排是：**审阅版完成 → 人工审阅 → 按反馈修改 → 素材与配置到位后准备上线**。每个阶段独立验收，不把下一阶段缺少的输入当作当前阶段的失败。

## 3. 最初提示词有哪些优点，哪里需要改

原提示词已经做对了几件重要的事：明确输出目录、指定技术基线、禁止虚构品牌和客户证据、要求实际运行检查，以及要求记录调整。这些都应保留。

需要改进的是目标之间的关系，而不是单纯增加更多要求。

| 原来的表述或安排 | 本次影响 | 更清楚的写法 |
| --- | --- | --- |
| 占位内容唯一来源，同时要求上线零占位 | 一开始就无法满足完整验收 | 审阅阶段允许明确占位；上线阶段才要求清零 |
| `spec.md` 是唯一规范，结尾又允许调整任何点 | “锁定项”与“最佳实践”的权限关系不清楚 | 明确哪些是不可变边界，哪些只是设计参考 |
| 附录 A 是内容唯一来源 | 文章只有主题、素材槽位没有内容时，补充范围不清楚 | 企业事实仅来自附录；允许自行编写中性界面文案与明确标注的提纲 |
| 确认邮件发出 | 未区分本地传输验证与真实邮箱投递 | 审阅验证本地 SMTP；上线验证真实收件与发信配置 |
| Core Web Vitals 无明显劣化 | 没有基线、测量环境和可重复判据 | 指定测量方式，记录数据与限制；有基线后再定回归阈值 |
| 每完成一个模块就跑检查 | 容易把所有检查机械重复一遍 | 模块完成跑相关检查，跨模块与最终交付跑完整检查 |
| 遇到真实内容缺失就停止 | 将上线依赖扩大成了整个开发的阻塞 | 先完成所有不依赖该输入的工作，再报告剩余阻塞 |
| “不要问，继续” | 可以减少打断，但不能解决矛盾或替代环境权限 | 明确可自主决定的范围，以及必须停止的外部操作 |

“按最佳实践”适合授权常规实现选择，不适合自动推翻商业事实、验收标准或发布权限。提示词应把这些边界直接写出来。

## 4. 执行时的选择原则，以及我应改进的地方

以下是依据可观察的实现与验证结果总结的决策原则，不是逐步内部推理记录。

### 先按最新授权确定当前交付物

你要求审阅版之后，缺少真实公司素材就不再阻止页面开发；你将规格改为参考之后，布局、标题与本地运行方式可以合理调整。但是，调整交付范围还应同步到 Goal 的验收条件，不能只体现在代码与聊天回复中。

### 保持事实诚实，让审阅版可用

使用明确标注的 SVG 概念图、占位提示与示例案例，避免把虚构图片、认证和客户故事包装成真实证据。保留 `noindex` 与严格上线 gate，使占位版本可审阅，同时仍能识别发布条件未满足。

### 优先采用易验证、易维护的实现

Astro、普通 CSS、设计令牌、共享组件与内容校验适合这个以内容展示为主的网站。原生 FAQ、菜单和筛选减少了客户端复杂度。本地 Node 适配器让表单和预览可直接运行，但它只是审阅阶段选择，不能证明原定云部署方式已经完成。

### 根据失败证据修正实现，也修正验证方法

类型检查暴露内容 schema 与类型推断问题后，修复对应代码；表单测试发现旧状态残留后，修复状态更新；客户端 JS 最初计数为零时，补计内联模块。后者尤其重要：绿色结果也可能来自测量遗漏，检查本身需要能解释它验证了什么。

### 对外部依赖和停止条件保持准确

没有真实邮件凭据，就验证本地邮件链路并记录差距；没有真实素材，就保留明显占位。网站审阅版完成可以结束这个阶段，但不能声称原来的正式上线目标已经完成。

我应承担的执行问题有三点：

1. **最初停止得过早。** 指出验收矛盾是正确的，但把它扩大为“不能开始任何实现”过于保守。更好的处理是说明完整上线受阻，并尽可能推进已授权且独立于真实素材的工作；如果阶段转换确实需要授权，只澄清这一处。
2. **范围变更后没有及时对齐持久目标。** 审阅版交付后，仍按旧上线目标继续审计，制造了不必要的重复阻塞报告。
3. **无新增输入时重复核查价值有限。** 缺少素材和凭据不会因重复运行 gate 而消失。应记录条件、保存交接，并根据当前目标结束或暂停；只有状态变化才重查。

这些问题不能全部归因于你的提示词。目标设计和执行判断都需要改进。

## 5. 更适合本项目的初始 `/goal` 提示词

下面是一份可用于项目起点的改写。已有网站时，应使用下一节的增量目标，避免重复搭建。

```text
/goal 在当前仓库的 goal-run/ 中完成可本地运行、供我审阅的官网版本。

阶段：这次只交付审阅版，不以正式上线作为完成条件。
参考：先读取 docs/spec.md 与附录 A。规格指导信息架构和设计；
本目标明确写出的范围与验收条件优先。不修改 docs/ 和 archive/。

事实边界：企业、产品、认证、客户事实只使用附录 A。
占位必须明显标识；不得虚构真实品牌、认证、客户评价或授权素材。
可以自行编写中性的导航、按钮、说明文案和明确标注的文章提纲。
缺少照片时使用明确标注的概念图或素材槽位。

实现：采用 Astro、普通 CSS 与设计令牌，完成规格中的十个模块、
共享壳层和必要详情页；兼顾移动端、键盘操作与表单状态。
选择最小且可维护的方案，常规可逆实现决定自行处理并记录理由。
不引入第三方客户端脚本，不发布网站，不向外部联系人发消息。

验收：实际通过 npm run build、npm run check:types、npm run test
和 npm run test:browser。验证路由、标题结构、关键键盘流程、
表单失败与成功状态，并用真实本地 SMTP 连接验证后端发送及 Reply-To。
记录性能测量环境与结果，不把本地结果当作线上 CWV 证明。

上线检查：保留严格 gate 和 noindex。审阅版含占位时，gate 应拒绝发布；
列明命中原因与上线待办，不通过删除标记或放宽规则让它变绿。
真实邮箱投递、真实公司内容和部署验收留到上线阶段。

迭代：先拟定简短计划，再实现与验证。模块完成跑相关检查，
交付前跑完整检查。失败时依据原因修复或换方案，不重复无效尝试。
缺少外部输入时，先完成所有独立工作；只在确实无法继续时报告阻塞。
常规选择不要询问，重大偏差与必要外部授权应明确报告。

完成条件：页面与上述审阅检查完成，README 写明启动方式，
REVIEW.md 写明设计调整、验证证据与上线待办，即完成本阶段并停止。
用户尚未给出审美反馈不影响这个阶段完成；不要自动进入上线阶段。
停止临时验证服务，报告文件位置与重新启动方法。
```

这份提示词的关键是“阶段与证据对应”，而不是它比原提示词更长。对于简单任务，可以压缩成“交付物、验收、边界、阻塞、完成动作”五项。

## 6. `/goal` 的使用方式与适用边界

官方将 Goals 定位为同一线程内跨回合持续推进的目标：终点清楚、路径可能变化的任务适合使用；一次性解释或小修改通常用普通提示即可。Goal 不是跨新会话自动继承的项目记忆。参见 [Using Goals in Codex](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)。

| 命令 | 用途 |
| --- | --- |
| `/goal <目标>` | 设置目标；支持更新的界面可用它调整目标 |
| `/goal` | 查看当前目标，核对范围与状态 |
| `/goal pause` | 暂停继续推进 |
| `/goal resume` | 恢复暂停目标 |
| `/goal clear` | 清除当前目标 |

命令生命周期见 [Goals 官方说明](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)；“创建或更新目标”及不同客户端的可用性说明见 [Codex 远程工程指南](https://developers.openai.com/blog/mastering-codex-remote-for-engineering)。应以当前客户端实际支持为准。

本项目适合采用以下工作方式：

1. **激活前检查目标是否可满足。** 用普通提示要求读取相关文件、指出验收矛盾和缺失输入。复杂任务先形成计划，再注册阶段目标。
2. **完成条件必须能观察。** “做得更专业”不能单独验收；“完成指定路由、验证表单、生成审阅报告”可以。视觉质量仍需要人工审阅，不能由测试替代。
3. **重大范围变化后检查 Goal。** 本次“上线”改成“审阅”应显式更新目标，再用 `/goal` 确认。若当前界面不能更新，就暂停并清除旧目标，重新设置。普通聊天可以修正方向，但不要假定保存的目标已经同步。
4. **预算控制与成功判定分开。** 如果界面提供正式预算设置，就使用它；预算耗尽只表示停止继续，并不表示完成。不要编造 `/goal --budget` 等未确认语法，也不要把正文里的时间要求当作已配置的硬限额。
5. **暂停目标与关闭服务分别处理。** `/goal pause` 管理任务推进；是否关闭网站进程还要明确执行和验证。本次二者都已完成，不能仅凭暂停状态推断端口关闭。
6. **把状态写进仓库。** 保存当前阶段、实际检查、剩余输入和下一步。新会话先读取这些文件，再设置新的目标。持续任务中的外部状态记录与“执行—观察—修复”循环，参见 [Run long horizon tasks with Codex](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)。

本次“三轮重复阻塞”的处理来自当时的执行规则，不应理解为所有 `/goal` 客户端通用的产品承诺。也不应为了凑次数而重复没有变化的失败检查。

“不要询问”应解释为：在已授权范围内自主决定常规事项。它不能自动提供邮件凭据、真实性证明或绕过环境审批。减少打断最有效的方法，是提前明确允许执行哪些本地操作，以及哪些外部动作不在本阶段范围内。

先用普通提示恢复上下文，而不是直接恢复旧的上线目标：

```text
读取 docs/study.md、docs/session-10.03.md、goal-run/REVIEW.md
和 goal-run/README.md，并检查现有文件。

spec.md 是参考。不要把历史检查当作当前代码的新验证结果。
先整理当前状态和我提供的审阅反馈，确定本次修改与验收范围。
不要重新搭建网站，也不要自动启动或恢复旧上线目标。
```

反馈明确后，再设置增量 Goal。以下方括号内容需要替换成实际要求：

```text
/goal 在现有 goal-run/ 上落实本次审阅反馈：[列出具体页面和修改要求]。
完成标准：[列出可观察的效果与验收方式]。

只修改反馈涉及的实现，必要的关联调整要记录原因。
执行与变更相关的检查；交付前验证构建、类型和受影响浏览器流程。
更新 REVIEW.md，说明修改、证据和未解决项；完成后停止本阶段。
```

正式上线应另设目标，并先确认真实资料、素材授权、邮件配置与部署环境已具备。目标中分别要求占位清零、真实收件验证、部署环境检查及上线报告；是否执行发布要单独写明授权范围。缺少这些输入时，先完成发布准备，而不是把“正式上线成功”设为当前必达终点。

## 8. 启动前的六个自查问题

- **交付物是什么？** 具体文件、页面、功能或报告，而非泛泛的“完善”。
- **这是哪个阶段？** 审阅、修改、发布准备还是正式发布。
- **完成证据是什么？** 命令结果、可复现操作、数据或人工验收项。
- **输入是否齐全？** 缺失输入是否真的阻断本阶段。
- **哪些决定已授权？** 文件范围、可逆操作、外部动作与权限边界。
- **结束时做什么？** 报告、保存交接、关闭服务、暂停或等待下一阶段。

对本项目，最有效的提示词改进是把“先做出能审阅的版本”写成正式目标，并在需求变化时同步更新持久目标。执行端则应更积极地完成独立工作，更准确地区分历史证据、当前验证与上线条件。
